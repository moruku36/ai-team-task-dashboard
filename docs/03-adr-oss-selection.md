# ADR-001：初版にKanboardを採用する

## 比較

| 観点 | Kanboard | Vikunja | 小規模自作 |
|---|---|---|---|
| ライセンス | MIT | 本体AGPL-3.0-or-later、desktop部分GPL-3.0-or-later | 新規コードのライセンス選択が必要。MIT等のOSS部品で構成可能 |
| Windows方式 | Windows/PHP対応。既存IIS/PHP、またはWSL2内でLinux構成 | Windowsデスクトップ版あり。ただし基本はフロントエンドで、別のサーバーが必要。ローカルはWSL2内のサーバーを候補にする | Node.js等の実行環境＋DBを配布/管理 |
| 主依存 | PHP 8.1以上と必須拡張、Webサーバー、SQLite等 | APIとUIを束ねたGoバイナリ、SQLite等。Dockerも選択可能 | UI、API、DB、認証、テストを自分たちで保守 |
| 標準の看板 | 列、タグ、担当、優先度、検索、履歴等 | 看板を含むタスク管理。APIも充実 | 必要機能だけ作れるが、完成品はまだない |
| スマホ | 公式にも小画面では使いにくい場合の注意あり。初回は一覧を評価 | Web/desktop/mobileの経路あり。実機での見やすさは未検証 | 最適化可能だが実装・アクセシビリティ試験が必要 |
| API | JSON-RPC。task、metadata、reference等 | 文書化されたAPI。現行ドキュメントはv1/v2の移行方針あり | 自由設計。認可・競合制御も実装責任 |
| export/backup | task等のCSV、API、SQLite+filesのバックアップ | CLI dump/restoreで設定・DB・filesを扱える | JSON/DB exportを自作 |
| 別ホスト移行 | 同じPHPスタックへ移しやすい | 同じバイナリ/コンテナへ移しやすい | 選択した構成次第。SQLite→Postgresは移行実装が必要 |
| 今回の最短性 | **標準機能と運用ルールで初版に到達** | 良い代替だが、初版の必要機能に対して選択項目が増える | 確実に短い根拠がないため採用しない |

## 決定と理由

Kanboardを改造せず開始する。狙いは「タスク状況を見やすくする」であり、「AIチーム統合基盤を先に作る」ことではない。追加フィールドは短い説明テンプレート、承認待ちはタグで表す。標準の限界は明記し、初版では単一更新者に絞る。

## 受け入れる弱点

- Kanboardはメンテナンスモードで、大きな新機能を期待する選択ではない。[S1](08-sources.md)
- 任意の独自項目を標準カードに表示すること、厳密な複数AI同時更新、承認エンジンは標準機能だけでは保証しない。
- Windowsの導入記事は古い旨の注意がある。稼働中の環境を確認せず、作業量や導入時間を断言しない。
- スマホの使い勝手が受入条件を満たさなければ、Vikunjaで同じ架空10件を比較するか、Phase 2Bの閲覧UIへ進む。最初から両製品を運用しない。

## 採用しない案

- VercelへPHPサーバー＋書込可能なSQLiteをそのまま移す案：ホスティングモデルが合わない。
- 初版から複数AIが直接書き込む自作看板：認証・競合・監査の保守負担が先行する。
- 「無料VPSが必ず確保できる」前提：供給・利用条件・休止・課金が未確定。
- Docker Desktopを必須にする案：既存の導入状態や利用条件を増やすため、今回は避ける。

## 見直し条件

スマホ受入失敗、保守停止/重大な未解決脆弱性、同時更新需要の増大、独自項目が主用途になる、月額上限の変更のいずれか。アプリ名の好みだけで移行せず、試験結果と保守コストで再判断する。
